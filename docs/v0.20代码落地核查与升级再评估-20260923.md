## 3. 对前序评估文档的修正与确认

1. **确认**：前序 B1–B8 破坏点清单与文档 v0.20 声称的适配点（Scheduler 构造参数、Request、FullAttentionSpec、KVConnector、等待队列）相互印证，两份独立分析看到的破坏面一致，可放心作为落地 checklist。
2. **修正一处**：前序文档说 rc1 的调度"没有上游继任者……默认走上游 V1 `Scheduler`"。更精确的机制是：rc1 通过 `patch/platform/patch_balance_schedule.py` 把 `EngineCoreProc.run_engine_core` 全局替换、并使平台默认 Scheduler 为 `BalanceScheduler`——关闭均衡开关时其 `schedule()` 委托父类，**效果**上等同上游调度，但"真实 Ascend 代码"的类身份是 `BalanceScheduler`。（前序调研的树列表被 API 截断导致漏看该 patch 目录，本次已直接向上游复核修正。）"prefill-first 无上游继任者"的判断**不变**。
3. **新增判断**：文档 v0.20 的 AST 加载方案（`lab/ascend_loader.py` 只执行 import、特性开关函数和 `BalanceScheduler` 类节点，排除 EngineCore 启动与全局 patch）是 CPU 实验台隔离边界的合理做法，比前序 A1（fork 移植）轻很多，且保留了原始类源码可追溯性。但它与 A2 一样**不含任何 Ascend 特有调度语义**（均衡/dynamic batch/profiling chunk/recompute 均不启用，prefill-first 已不存在）——相对 0.11 工程"能跑真实 prefill-first 分支"是一项能力回退，文档自己也把 `ascend-prefill-first.json` 改名为 `ascend-unchunked.json` 并声明"不再称为 Ascend 独有的 prefill-first"。

## 4. 风险

- **版本误标是当前最大风险**：`mooncake-cpu-lab-v0.20` 名称 + v0.20 设计文档 + `results/`（实为 0.11.0 产出）组合起来，足以让后续读者/协作者/论文引用误信存在一套 v0.20.2 验证结果。仓库一旦推送，误标随历史扩散。
- **可复现性断裂**：按 v0.20 文档的安装说明（torch 2.11、transformers 5.5.3）去跑当前代码会因 `prepare_vllm_source.py` 的 `0.11.0` 检查直接退出；反之按 0.11 环境跑 `mooncake-cpu-lab-v0.20` 会得到"名为 v0.20、实为 0.11"的结果。
- **双副本漂移**：两个内容相同的文件夹今后任何一侧被单独修改，diff 将失去"版本对照"的意义。
